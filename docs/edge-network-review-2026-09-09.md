# Network model and protocol audit: September 9, 2026

## Evidence and scope

[Reviewed] All 218 inventory entries received a network-scope review. There are 117 entries with named network models, protocol interfaces, integrations, or trace types; other entries retain their specific project scope or actual source-access outcome. This is a documentation and source-code review, not installation or runtime certification of all projects.

[Changed] Added 311 distinct resource/protocol assignments across 102 resources. The network filter now contains 140 choices. ns-3 has 46 labels, including separately identified external integrations. Seventy additional official source records accompany the network review. Existing pinned project evidence is reused where appropriate.

[Policy] `network.json` owns the protocol facet. Its entries distinguish `packet`, `abstract`, `runtime`, `service`, `extension`, and `data`. These describe different meanings of support; a common protocol label does not guarantee equal fidelity. No labels are inferred automatically from engines, dependencies, README keywords, survey marks, author biographies, or links to unrelated projects.

[Policy] `scope-only` means the inspected project description identifies its function without establishing a named networking interface in this review. It is not a claim that the entire project cannot communicate. `source-unavailable` preserves a concrete access failure; references remain outside tool comparison.

## Material corrections

- [Source] ns-3 Internet, Wi-Fi, routing, LTE/EPC, LR-WPAN, 6LoWPAN, Zigbee, UAN and TCP models use pinned source documentation. Global routing does not establish OSPF message simulation. CSMA provides a subset of Ethernet behavior. 5G-LENA, LoRaWAN and OFSID require additional installation and compatible versions.
- [Source] MEC-simulator schedules task objects through a radio-delay model. Its ns-3 dependency does not justify LTE/IP packet-stack labels.
- [Source] PureEdgeSim communication technologies and IoTSim-Edge CoAP/XMPP settings are abstract performance/energy models.
- [Source] SimGrid analytical TCP models are distinct from its separately configured ns-3 adapter. Only the interfaces actually used by that adapter are tagged.
- [Source] OMNeT++ protocol labels explicitly require INET. Cooja protocol support belongs to the selected Contiki-NG firmware and configuration.
- [Source] Neurosurgeon’s UDP server and DeepThings’ socket implementation provide stronger evidence than stale or terse README wording.
- [Source] ForestHub OPC UA/Modbus roadmap items, ns3-ai historical NR experiments, KitNET’s separate Kitsune capture system, and generic neural-network layer names are not converted into protocol support.
- [Source] Packet Tracer’s Cisco-hosted protocol list is explicitly a historical 5.1 teaching-model baseline; EdgeX’s historical device-service list also retains its version boundary.
